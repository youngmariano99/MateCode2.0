# Plan — Auditoría MateCode 2.0

Checklist de seguimiento de la auditoría técnica (ver informe completo entregado como artifact). Cada ítem tiene la decisión tomada, breve y concisa, para no volver a discutirla cada vez.

**Contexto que gobierna todas las decisiones: MateCode es mono-usuario.** Es una herramienta personal de Mariano, nadie más la usa. Todo lo que en el estándar de Nodexa está pensado para multi-tenant (RLS por `cliente_id`, aislamiento entre inquilinos, feature flags por cliente) **no aplica acá** salvo que se indique lo contrario. Donde el estándar protege contra "otro cliente lea mis datos", acá no hay otro cliente.

## Backend — Sync e integridad de datos

- [x] Las escrituras hechas online no se encolan automáticamente (solo offline). **Resuelto** — se quitó el `if (!online)` en los 9 use-cases que lo tenían (`crear/actualizar-proyecto`, `gestionar-tarea`, `CrmUseCase`, `registrar-visita`, `crear/actualizar-documento`); ahora encolan siempre. En `registrar-visita` también se corrigió un caso aparte: la actualización de `historialVisitas` del cliente se escribía en Dexie pero nunca se encolaba, ni offline ni online — ahora sí. En Agencia (que escribe directo a Supabase cuando hay conexión) se agregó fallback: si el escritor directo falla pese a estar "online", ahora encola en vez de perder el alta. También se corrigió `SyncProvider` — antes solo procesaba la cola al pasar de offline a online; ahora observa la cola en vivo (`useLiveQuery`) y la procesa en cuanto aparece un evento pendiente estando online, sin esperar un cambio de conectividad. Verificado con typecheck, eslint, 114/114 tests y `npm run build` limpios.
- [x] El respaldo manual (`respaldarTodoEnSupabase`) no cubre todas las tablas del Segundo Cerebro. **Resuelto indirectamente** — con el punto anterior, la cola es ahora el camino real de sync; el botón "Respaldar Nube" queda como respaldo de emergencia, no como mecanismo principal. No se tocó su lista de tablas porque dejó de ser crítico.
- [x] Escritura local y encolado no son atómicos (dos `await` sueltos). **Resuelto en los use-cases de mayor tráfico**: `crear/actualizar-proyecto`, `gestionar-tarea` (crear/actualizar/eliminar), `CrmUseCase` (incluidas las operaciones masivas, ahora atómicas como bloque completo), `registrar-visita` (visita + cliente en una sola transacción), `crear/actualizar-documento`, y el camino offline de Agencia — todos envueltos en `db.transaction("rw", [...], async () => {...})`. **Decisión: diferir en el resto** (personal/*, contenido, contacto-frio — ~60 call sites restantes): la ventana de riesgo real es que el navegador se cierre en el intervalo de milisegundos entre dos `await` seguidos de IndexedDB estando offline — muy improbable, y tocar 60+ sitios mecánicamente no es proporcional a ese riesgo. Se puede retomar caso por caso si alguna vez se confirma un evento perdido ahí.
- [x] Conflictos se resuelven "el que llega último gana"; `ConflictService` (LWW por timestamp) existe pero no se usa. **Resuelto** — se extrajo la comparación pura a `src/shared/utilidades/resolucion-conflictos.ts` (sin dependencia de Dexie, usable en servidor) y se conectó en ambas rutas de sync (`[table]/route.ts` y `bulk/route.ts`): antes de cada upsert se compara `actualizadoEn` contra lo que ya hay en Postgres: si el servidor tiene una versión más nueva, no se sobreescribe. `ConflictService` (cliente) ahora delega en la misma función compartida.
- [x] `bulk/route.ts` no aísla fallos parciales (una fila mala tira abajo todo el request). **Resuelto** — se pasó de una única transacción para todo el payload a una transacción por tabla; si una tabla falla, las demás ya guardadas no se revierten. La respuesta ahora incluye `tablasOk`/`tablasConError` para saber exactamente qué pasó, y `respaldarTodoEnSupabase` revisa esa respuesta y lanza error si alguna tabla falló (antes lo ignoraba silenciosamente).
- [x] No hay tests de escenarios de falla de sync (red cortada a mitad, conflicto real, reintentos agotados). **Resuelto** — `src/shared/utilidades/sync-fallos.test.ts` (8 tests nuevos): la función de resolución de conflictos con sus casos límite, y `SyncService.sincronizar()` contra una red inalcanzable real (sin mock) verificando que un evento roto no corta la cola, que los reintentos se registran por evento, y que uno que agota `MAX_INTENTOS_SYNC` queda marcado como conflicto para revisión manual sin volver a tocar la red. Total suite: 122/122.
- [ ] Coerción automática de fechas por nombre de campo (`dateFields`). **Decisión: no tocar el mecanismo, ya está mitigado con la convención de nombres** (`diaTarea` en vez de `fecha`). Mantener esa convención documentada para cualquier campo nuevo.
- [ ] Sin backoff exponencial entre reintentos de cola. **Decisión: diferir**, impacto bajo, no bloquea el resto de la cola.

## Backend — Seguridad

- [x] `/api/ai/execute` ejecuta comandos de shell decididos por el modelo sin autenticación. **Resuelto** — el middleware ahora exige sesión en todo `/api/**` (ver ítem siguiente), así que este endpoint quedó cerrado sin tocar su lógica interna (sigue usándose desde `conveyor-belt-focus-view.tsx`).
- [x] Rutas `/api/**` sin gate de autenticación en el middleware. **Resuelto** — `src/middleware.ts` ahora devuelve 401 JSON (`No autenticado.`) para cualquier request a `/api/**` sin sesión Supabase, en vez de dejarla pasar. Matcher extendido a `/api/:path*`. Verificado en el navegador: `/api/sync/bulk` sin sesión → 401; `/dashboard` sin sesión → sigue redirigiendo a `/login` como antes. Typecheck, eslint y 114/114 tests sin regresiones.
- [ ] Cero validación Zod en las rutas de API. **Decisión: arreglar**, fail-fast en la puerta.
- [ ] Mensajes de error crudos de Postgres/Drizzle expuestos al cliente. **Decisión: arreglar, prioridad baja** — loguear el detalle server-side, devolver mensaje genérico.
- [ ] Ausencia de RLS multi-tenant en Postgres. **Decisión: no aplica.** Mono-usuario, no hay otro `cliente_id` del que aislarse. No se implementa.

Los otros 14 escribían directo a Dexie y ahí se quedaban — mismo bug de "nunca sincroniza" que ya había aparecido con proyectos/pagos/documentos, pero repetido en pantallas centrales: el tablero de backlog completo (crear/editar/borrar épicas, historias y tareas), el sprint planner (crear sprint, iniciar, reasignar historias, cierre con rollover), la importación de proyectos vía JSON, la importación de backlog/épicas/historias/sprints vía JSON, la conversión de prospecto de Territorio a cliente CRM, y el flujo de ejecución automática con Antigravity (metadata de la ejecución, checkpoints, iteraciones, checklist, cierre de ticket). **Se agregó `QueueService.encolar` en cada uno de esos 14 archivos**, en transacción con la escritura local, siguiendo el mismo patrón ya establecido — sin mover el código a use-cases nuevos (eso sí sigue pendiente como mejora de arquitectura, ver abajo), porque lo urgente era cerrar la fuga de datos, no reordenar carpetas. Los ~35 archivos restantes solo leen (`useLiveQuery`) — arquitectónicamente impuro pero sin riesgo de pérdida de datos, **diferido**: mover esas lecturas a use-cases es trabajo de prolijidad, no de seguridad, y no es proporcional hacerlo ahora. Un solo cambio en la ruta arregla automáticamente todos los use-cases que ya encolaban "eliminar" correctamente. **Decisión sobre el borrado local (Dexie/IndexedDB): se deja físico a propósito** — es la caché de este navegador, no la fuente de verdad; el registro sobrevive en Supabase marcado `eliminadoEn`, recuperable ahí si hiciera falta. Cambiar el borrado local a lógico obligaría a filtrar `eliminado` en cada vista de lista del proyecto, un costo no proporcional al riesgo real en un sistema mono-usuario.

  - **La tabla `documentos` (Contratos & Documentos) no existía en Supabase ni en el mapeo de sync** — todo alta/edición/borrado de un documento inteligente quedaba agotando reintentos en la cola para siempre sin que nadie lo notara; el documento nunca salía del navegador. Se creó la tabla en Postgres (migración aplicada directamente) con columnas de auditoría desde el arranque (`eliminadoEn`), se agregó a `tableMapper` en ambas rutas de sync, y se corrigió `contratos/page.tsx` (que tampoco encolaba el borrado).
  - `pagos/page.tsx` — borraba un pago (dato financiero) solo local, sin encolar nada. Ahora encola "eliminar" en transacción con el borrado local.

  Verificado: typecheck, eslint, 122/122 tests, `npm run build` limpios.

## Base de datos

- [x] FKs (`proyectoId`, `epicaId`, `sprintId`, etc.) sin `.references()` real, solo convención de nombre. **Resuelto** — antes de agregar cada constraint se chequeó por huérfanos (filas hijas apuntando a un padre que ya no existe). 7 de 8 relaciones (`epicas/sprints/historias/tareas → proyectos`, `historias → epicas`, `historias → sprints`, `tareas → historias`) no tenían ningún huérfano, se agregaron como FK real normal. `task_executions.proyecto_id` tenía 9 filas huérfanas — resto de dos proyectos borrados antes de que el borrado pasara a ser lógico (ver bloque de sync arriba) — se agregó igual la FK pero como `NOT VALID`: no exige limpiar esas 9 filas viejas, pero valida cualquier inserción nueva de acá en adelante. `schema.ts` actualizado con `.references()` reales en los 8 campos.
- [x] Cero índices explícitos en ~70 tablas. **Resuelto** — se indexaron automáticamente (vía `information_schema`, sin listarlas a mano) todas las columnas `proyecto_id`, `agencia_id`, `cliente_id` y `estado` de cada tabla que las tiene: 65 índices creados. No se declararon en `schema.ts` con `.index()` porque este proyecto no usa `drizzle-kit push` (cuelga en este entorno, migraciones siempre se aplicaron a mano) — la base de datos real ya los tiene, que es lo que importa para el rendimiento.
- [x] Arrays guardados como `text()` ("JSON string[]") en vez de `jsonb` o tabla relacional (`dolorTags`, `tagsResultado`, `canales`, etc.). **Resuelto** — las 8 columnas (`ficha_digital.dolorTags`, `intento_contacto.tagsResultado`, `contenido.canales`, `sprints.miembros`, `historias.dependencias`, `historias.etiquetas`, `proyecto_estado_tecnico.dependencias`, `proyecto_estado_tecnico.esquemaDb`) se convirtieron a `jsonb` con `ALTER COLUMN ... USING NULLIF(col,'')::jsonb` (verificado sin corromper los datos existentes). `schema.ts` actualizado, y las dos rutas de sync ya no las stringifican antes de guardar (solo lo siguen haciendo los campos que de verdad se quedan como `text`, como `metadata` de `task_executions`).
- [x] Tablas del Segundo Cerebro sin columnas de auditoría (`eliminadoEn`). **Resuelto** — se agregó `eliminado_en timestamp` a las 14 tablas que no lo tenían (`ciclo_semanal`, `idea_contenido`, `plantilla_guion`, `contenido`, `catalogo_kpi_contenido`, `inbox_item`, `tarea_diaria`, `tarea_pendiente`, `habito_definicion`, `habito_registro`, `catalogo_ejercicio`, `bloque_entrenamiento`, `registro_actividad`, `objetivo_cuantificable`). Como la ruta de sync ya soft-deletea automáticamente cualquier tabla con esta columna (arreglo del bloque de arriba), estas 14 tablas ya quedan cubiertas sin tocar código de use-cases.

  Verificado: typecheck, eslint, 122/122 tests, `npm run build`, y lectura directa de una fila migrada para confirmar que el `jsonb` no quedó corrupto.
